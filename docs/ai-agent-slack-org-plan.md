# AI 에이전트 조직 기획서

## 1. 목적 및 배경

- 사적인 용도의 프로젝트.
- 표면적으로는 일반 소규모 기업/조직 형태를 취하지만, 실질적으로는 **사용자 1인 + AI 에이전트들**로 운영되는 조직을 지향함.
- 최종 이상향: Slack 상에서 AI 에이전트와 사람의 구별이 어려운 상태.

## 2. 통신 인프라 (Slack 기반)

### 2.1 설계 원칙 — 사람과 동일한 업무 방식

AI 에이전트가 편한 방식(API 직접 호출 등)이 아니라, **사람이 일하는 것과 정확히 동일한 데스크톱 환경·방식으로 업무에 참여**하는 것을 원칙으로 함. 조직 구성원 전체(사람, Claude 에이전트, GPT 에이전트)가 같은 업무 방식으로 통일되는 것이 목적. 이 원칙은 발신 방식과 인터럽트 처리 방식 설계에 직접 반영됨.

### 2.2 수신·발신 구조

수신과 발신을 다른 방식으로 처리하는 하이브리드 구조로 설계함.

| 구분                        | 방식                                                                       | 이유                                                                                                                                                                                                                                                                         |
| --------------------------- | -------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 수신 (사용자 → 에이전트)    | **Socket Mode** + 에이전트 계정 **대신(on behalf of users) 구독한 이벤트** | 아웃바운드 웹소켓 연결만 사용, 집 네트워크에 인바운드 포트를 열 필요 없음. 실시간성이 중요하고 사람의 "알아채는 방식"을 굳이 흉내 낼 실익이 없어 API 방식 유지. 봇 이벤트로는 사람이 에이전트 멤버 계정에 보낸 DM을 받을 수 없어 사용자 이벤트로 확정 (2026-10-10, 1차 구현) |
| 발신 (에이전트 → 사용자/팀) | **GUI 자동화 (컴퓨터 사용/Computer Use)**                                  | API로 직접 메시지를 보내지 않고, Slack 클라이언트(데스크톱 앱 또는 브라우저 웹앱)를 열어 스크린샷을 찍고 그 안에서 답장 버튼·입력창·전송 버튼의 좌표를 파악한 뒤, 마우스·키보드를 직접 조작해 사람과 동일한 방식으로 메시지 전송                                             |

- API 방식(`chat.postMessage`)으로 보내도 "APP" 배지 없이 사람 계정 명의로 나가는 결과는 GUI 자동화와 동일함. 즉 GUI 자동화를 택한 이유는 사람처럼 보이기 위함이 아니라, **"사람과 동일한 환경·방식으로 참여한다"는 조직 철학 자체를 구현하기 위함**임.
- Slack 데스크톱 앱과 브라우저 웹앱 사이에는 원칙상 차이를 두지 않음 (실제로 다수의 사람도 웹앱으로 Slack을 사용함). 따라서 에이전트가 데스크톱 앱 대신 웹앱을 쓰는 것도 원칙에서 벗어나지 않음.
- 토큰 (1차 구현에서 확정):
  - 데스크톱 앱 로그인은 토큰과 무관하게 앱 자체 로그인으로 유지됨.
  - 에이전트 계정이 승인한 User token(`xoxp-`)은 **읽기 scope만** 가진 채 이벤트 구독과 이름 조회에 쓰임. 쓰기 scope가 하나라도 있으면 에이전트가 시작을 거부함.
  - 봇 토큰(`xoxb-`)은 쓰지 않음.
  - (이전 안: "User token은 데스크톱 앱 로그인 유지용" — 폐기)

### 2.3 인터럽트 정책 (수신 시 작업 중단 처리)

에이전트가 다른 작업을 수행하는 도중 Slack 메시지가 도착했을 때, 이를 어떻게 처리할지에 대한 정책.

| 방식                          | 개념                                                                                               | 채택 여부                                                                                           |
| ----------------------------- | -------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| 선점형 인터럽트 (preemptive)  | 진행 상태와 무관하게 즉시 강제로 작업을 중단시킴 (SDK의 `interrupt()` 등)                          | **제외** — 사람이 일하는 방식과 맞지 않고, 현재 Claude Agent SDK 단에서도 안정성 이슈가 보고된 상태 |
| 협조적 인터럽트 (cooperative) | 에이전트가 스스로 "중단해도 안전한 지점"(원자적 작업 단위 경계)에 도달했을 때 상태를 저장하고 확인 | **채택**                                                                                            |

- 사람이 작업 중 알림이 오면 하던 동작(문장 하나, 함수 하나 등)까지는 마무리하고 확인하는 것과 동일한 방식.
- 리스너(Socket Mode)는 항상 가볍게 대기하며 메시지 도착을 즉시 감지하되, 실제 작업 흐름에 대한 개입은 에이전트가 스스로 다음 분기점에서 확인하는 시점까지 지연됨.
- 조직의 업무 방식 원칙(2.1)과 일관됨.
- 1차 구현: 새 메시지는 도구 결과 끝의 🔔 알림으로만 보이고, 에이전트가 안전한 지점에서 `inbox_peek`(보기) / `inbox_take`(이번 턴에 처리) / `inbox_yield`(메모 남기고 일시정지 후 재개)를 고름.

### 2.4 신원(Identity) 방식

- Slack Bot App은 메시지마다 표시 이름/아이콘을 바꿔 여러 캐릭터처럼 보이게 할 수 없음 (Slack 플랫폼 제약).
- "사람과 구별 어려운" 목표를 달성하려면 **에이전트 1명당 별도의 정식 Slack Member 계정**이 필요함.
  - 각 계정은 고유 이메일, 프로필 사진, 이름, 직함을 가짐.
  - 유료 워크스페이스일 경우 인원수만큼 seat 비용 발생.
  - Slack API 이용약관상 사람인 척하는 자동화 계정에 대한 제약이 있으나, 완전히 사적이고 외부인이 없는 워크스페이스에서는 실무적 리스크가 낮음. 외부인이 합류하는 시점에 재검토 필요.

### 2.5 실행 엔진 (로컬 에이전트)

- 에이전트의 실제 작업 실행은 집 컴퓨터(사용자 네트워크 내부)에서 이루어짐.
- 실행 결과나 판단이 필요한 시점에만 Slack으로 커뮤니케이션.
- Claude 기반 에이전트: Claude Agent SDK 또는 Claude Code 헤드리스 모드 활용.
  - **1차 구현: Claude Code CLI(`claude -p`)**, 장비에 로그인된 Claude 계정 사용.
  - 화면·마우스·키보드 도구는 엔진과 무관한 localhost MCP 서버로 제공되어, GPT 에이전트도 같은 책상을 쓸 수 있음.
- GPT 기반 에이전트: OpenAI API 기반의 별도 실행 프레임워크 필요 (Claude 쪽과 완전히 다른 엔진이며, 같은 코드베이스를 모델만 바꿔 재사용할 수 없음).
- 수신 구조(Socket Mode + 사용자 대신 구독한 이벤트), 발신 구조(GUI 자동화), 인터럽트 정책(협조적 인터럽트)은 Claude 에이전트와 GPT 에이전트 모두에 동일하게 적용되는 공통 원칙.

## 3. 채널 구조

- **팀 채널** (예: `#team`) — 전 구성원 참여. 에이전트 간 대화도 이 채널에 공개하여 "실제 사무실"에 가까운 느낌을 의도적으로 조성.
- **개별 DM** — 사용자 ↔ 각 에이전트 1:1. 사적인 질문/보고에 사용.

## 4. 조직 구조

### 4.1 소통 방식

- **평평한(flat) 팀** 구조. 사용자가 중간 창구(비서/팀장) 없이 모든 구성원과 직접 대화.

### 4.2 시작 구성

업무 영역보다 **"어떤 AI 엔진으로 이루어진 인격체인가"**를 기준으로 최소 구성부터 시작하기로 결정.

| 구성원 | 정체                 | 비고                                                                |
| ------ | -------------------- | ------------------------------------------------------------------- |
| 1      | 사용자 (사람)        | 조직 내 위치(대표/동료 등)는 아직 미정 — 자연스럽게 정해지도록 보류 |
| 2      | Claude 기반 에이전트 | 1차 구현 완료 — `에이전트1`(임시 이름)                              |
| 3      | GPT 기반 에이전트    |                                                                     |

- 아직 업무는 배정되지 않은 상태로 시작.
- 참고로 논의 중 나왔던 유력 업무 후보: **코딩/개발 작업**, **정보 수집/리서치** (사용자가 현재 가장 많은 시간을 쓰는 반복 업무로 꼽음). 추후 역할 배분 시 참고 가능.

## 5. 기술적으로 짚어둔 위험 요소 (향후 설계 시 반영 필요)

- **에이전트 간 대화 루프 문제**: 팀 채널에서 에이전트끼리 대화가 공개되는 구조를 택했으므로, 무한 루프·비용 폭증을 막을 정지 규칙이 필요함 (예: `@멘션` 기반 트리거, 스레드당 최대 왕복 횟수 제한, 대화 종료 판단 로직 등).
  - 1차 구현에 반영: 채널에서는 멘션·참여한 스레드만 받고, 한 채널에서 사람 없이 에이전트가 `MAX_AGENT_EXCHANGES`(기본 4)회 말하면 사람이 말할 때까지 사람에게만 답함. 실전 검증은 두 번째 에이전트가 생긴 뒤.
- **질문-대기-재개 패턴**: 에이전트가 작업 중 사용자 판단이 필요할 때, 프로세스를 블로킹하지 않고 상태를 저장한 뒤 사용자 응답 시 세션을 재개하는 방식 설계 필요.
  - 1차 구현에 일부 반영: 대화(채널·DM)마다 엔진 세션을 이어 쓰고, `inbox_yield`로 멈춘 일을 메모와 함께 재개. 대기열과 멈춘 일은 재시작해도 남음.

## 6. 장비(하드웨어)

### 6.1 원칙 — 에이전트당 장비 1:1

- GUI 자동화 방식(마우스/키보드 직접 조작)을 채택했기 때문에, 한 장비에서 여러 에이전트가 동시에 화면을 조작하면 충돌이 발생함.
- **에이전트 1명당 별도의 물리적 장비를 배정하는 것을 고정 원칙으로 함** (변경 불가).
- 장비 수는 곧 에이전트 수와 동일. 현재 시작 구성(Claude 에이전트 1 + GPT 에이전트 1) 기준 장비 2대 필요.
- 1차 구현에서 Claude 에이전트의 장비는 MacBook Pro 한 대 (launchd 상시 실행). 화면이 켜져 있어야 하므로 덮개를 열어 두거나 외부 모니터/HDMI 더미 플러그가 필요.

### 6.2 권장 스펙 (1대 기준)

로컬 장비는 실제 추론(reasoning)을 수행하지 않고 화면 캡처·마우스/키보드 조작·앱 실행만 담당하므로 고성능이 불필요함. 대신 24시간 상시 가동을 전제로 전력·발열·안정성이 우선순위.

| 항목     | 권장 사양                                               | 이유                                                             |
| -------- | ------------------------------------------------------- | ---------------------------------------------------------------- |
| 폼팩터   | 노트북보다 **미니PC** 권장 (NUC류, Mac mini 등)         | 배터리 열화 문제 없음, 냉각 여유, 모니터 연결이 기본 전제인 구조 |
| CPU      | Intel N100/N200급 또는 Ryzen U시리즈 등 저전력 모바일급 | 로컬 추론 없음, 전력·발열이 성능보다 중요                        |
| RAM      | 16GB (여유 두려면 32GB)                                 | Slack·브라우저 등 Electron 앱의 메모리 사용량이 의외로 큼        |
| 저장장치 | SSD 256~512GB                                           | HDD는 24/7 가동 시 기계적 마모에 불리                            |
| GPU      | 내장 그래픽으로 충분                                    | 로컬 렌더링 부담이 모니터 1대 출력 수준뿐                        |
| 네트워크 | 유선 이더넷 우선                                        | Wi-Fi 대비 Socket Mode 연결 안정성이 높음                        |
| 전원     | 유휴 전력 소비 낮고 저소음/팬리스 선호                  | 24시간 상시 가동 전제                                            |

- GUI 자동화의 타이밍 신뢰성 때문에 "사람이 답답하다고 느끼는 수준"의 저성능은 오히려 불리할 수 있음 — 렌더링 지연으로 스크린샷 시점과 실제 화면 상태가 어긋나는 오류 발생 가능. 다만 이는 고성능이 필요하다는 의미가 아니라 매끄러운 동작을 위한 RAM 등 최소 여유가 필요하다는 의미.

### 6.3 후보 장비 — 라즈베리파이 + 우분투

- Slack 공식 데스크톱 앱은 x86_64만 지원하고 ARM(라즈베리파이)은 지원하지 않음. 단, **발신 시 브라우저 기반 Slack 웹앱을 사용**하기로 결정했으므로 (데스크톱 앱·웹앱 간 원칙상 차등 없음, 2.2 참고) 이 제약은 우회 가능.
- 저전력·저발열·모니터(HDMI) 연결이라는 24/7 가동 조건에 부합하고, 미니PC 대비 비용이 훨씬 저렴해 에이전트당 1:1 장비 원칙(6.1)을 여러 대로 확장할 때 유리함.
- 주의점: RAM이 보통 8GB가 상한이라 미니PC 대비 여유가 적고, 싱글코어 성능도 낮아 브라우저 기반 GUI 자동화 시 렌더링 지연에 조금 더 취약할 수 있음. 실사용 검증 필요.
- 1차 구현의 손(데스크) 드라이버는 macOS 전용. 라즈베리파이로 가려면 Linux 데스크 드라이버를 추가해야 함 (나머지는 그대로 재사용).

## 8. 참고 — Slack 앱 설정 절차 (1차 구현에서 확정)

에이전트마다 앱 하나. 봇은 만들지 않음.

1. api.slack.com/apps 에서 App 생성 (관리자 계정)
2. Socket Mode 활성화 + App-Level Token 생성 (scope `connections:write`) → `SLACK_APP_TOKEN`(`xapp-`)
3. User Token Scopes (읽기만): `im:history`, `mpim:history`, `channels:history`, `groups:history`, `users:read`, `channels:read`, `groups:read`, `im:read`, `mpim:read`. 쓰기 scope(`chat:write` 등)는 넣지 않음
4. Event Subscriptions → **Subscribe to events on behalf of users**: `message.im`, `message.mpim`, `message.channels`, `message.groups`
5. Collaborators에 에이전트 계정 추가 → **에이전트 계정으로** Install to Workspace → User OAuth Token(`xoxp-`) → `SLACK_READ_TOKEN`
6. 에이전트 계정을 필요한 채널에 초대 (봇 초대 불필요)
